# Learn Anything

Name a topic, pick **Normal** or **Deep**, and get a saved course of written
lessons with one final quiz at the end.

This is a local-first Next.js app. Courses are generated by a small pipeline of
model calls, stored in SQLite, and safe to resume if generation dies halfway.

## Quick start

Requirements: Node 20+ and pnpm.

```bash
pnpm install

# .env.local already exists with an empty key slot. Add your key:
#   ANTHROPIC_API_KEY=sk-ant-...
pnpm models          # confirms the configured model id is available
pnpm dev             # http://localhost:3000
```

Migrations run automatically on first database access. The database lives at
`data/learn.db`. The local app has no auth and no accounts.

Without an API key you can still exercise the read and quiz UI with a seeded
course:

```bash
pnpm seed:demo
# prints a topic id; open http://localhost:3000/topics/<id>
```

## Run with Docker

The image runs `next start`, so the in-process worker survives for background
generation.

```bash
# .env.local supplies ANTHROPIC_API_KEY; it is not baked into the image
docker compose up --build
```

Open **http://localhost:3000**. SQLite lives in the `learn-data` named volume.

```bash
docker compose logs -f app
docker compose down          # keep data
docker compose down -v       # delete the Docker database
```

The compose file also contains a commented bind mount if you want the
repository's `data/learn.db` directly:

```yaml
volumes:
  - ./data:/app/data
```

Stop `pnpm dev` before starting the container; both use port 3000. The CLI
(`pnpm gen`, `pnpm seed:demo`) is not installed in the runtime image. To use the
host database inside Docker, stop the container, copy the checkpointed file,
and start it again:

```bash
docker compose stop app
node -e "const D=require('better-sqlite3');const db=new D('./data/learn.db');db.pragma('wal_checkpoint(TRUNCATE)');db.close()"
docker compose cp data/learn.db app:/app/data/learn.db
docker compose start app
```

## Generate a course from the CLI

Build the pipeline before the UI is the rule here, and `pnpm gen` is the fastest
way to inspect lesson quality.

```bash
pnpm gen "Photosynthesis"
pnpm gen "Photosynthesis" --deep
pnpm gen "Linear algebra" --deep --out data/linear-algebra.md
```

Each run prints stages, token usage, an estimated cost, and writes the course as
one readable Markdown file under `data/`. The topic is also in the database, so
it appears in the app.

## What happens when you create a course

```
topic + mode
   │
   ├─ 1. ANALYZE      one call, both modes; extracts 3-6 course concepts
   │
   ├─ 2. DECOMPOSE    deep only: 3-4 ordered subtopics
   │
   ├─ 3. OUTLINE      1 call per unit; 4-5 lessons per deep unit, max 3 in flight
   │
   └─ 4. LESSON+QUIZ  1 call per lesson; teaching + assignment + final-quiz questions, max 3 in flight
```

Normal mode runs 1, 3, 4. Deep mode runs 1, 2, 3, 4.

Every stage writes its result before moving on. A retry resumes at the first
unfinished lesson, so finished work is never re-paid for. The worker is
in-process and assumes one long-lived Node process; on boot it re-enqueues any
course left `queued` or `generating`.

Generation is always asynchronous. `POST /api/topics` returns an id immediately
and the UI polls `/api/topics/:id/progress`.

## Stack and layout

Next.js App Router · TypeScript · SQLite + Drizzle · Anthropic SDK · Zod ·
Tailwind · `react-markdown` + `remark-gfm`.

```
app/                    pages and route handlers
  api/                  HTTP surface
  topics/               course and lesson screens
src/
  ai/                   Anthropic client, Zod contracts, prompts, repair pass
  db/                   schema, client, migrations, queries
  pipeline/             run, worker, stages, concurrency cap
  quiz/                 grade, lint, write-time shuffle, read serializers
  ui/                   components and client interactions
scripts/gen.ts          CLI course generator
scripts/models.ts       verify the configured model id
scripts/seed-demo.ts    token-free demo course for UI work

postman/                OpenAPI spec, Postman v3 collection, local environment
```

## Design notes that matter

**Answers never reach the browser before submission.** `src/quiz/serialize.ts`
is the security boundary. It strips `answer_json` and `explanation`; the API and
the server-rendered lesson page both use it. A test asserts that no read payload
contains either field or the explanation text.

**Options are shuffled at write time.** For `order` questions the stored options
are deliberately scrambled and the answer is the id sequence. The browser can
render the stored order verbatim; no seed plumbing and nothing to leak.

**Grading is a pure server-side function.** `src/quiz/grade.ts` handles
`true_false`, `radio`, `multi` (exact set, all-or-nothing), and `order` (exact
sequence). Client-provided correctness is ignored. Attempts and answers are
stored in one transaction, with the raw response kept for re-grading.

**Structured output is validated, then linted, then repaired.** Zod
schemas in `src/ai/schemas.ts` are the single source of truth for both native
structured outputs and the forced-tool fallback. `src/quiz/lint.ts` catches
duplicate options, wrong correct-counts, disallowed `order` questions, negated
stems, "all of the above", answers missing from the lesson, missing comparison
tables, repeated visual kinds, generic headings, malformed comparison rows,
missing assignments, and lessons outside the word budget. Either failure
triggers a focused repair call that includes the validator error verbatim.
Lessons get up to three focused repairs because a six-question quiz can have
more than one independent failure. Style and word-count problems are soft: they
are logged, but do not sink an otherwise valid lesson.

**Core concepts are course-level, not lesson-level.** The analyze step extracts
3-6 concepts for the whole topic. Every lesson then chooses 1-3
`focus_concept_ids` from that list, builds on them, and cannot invent new
concepts. The topic page shows the full set; the lesson page shows the focused
subset with "concept X of Y" labels.

**The lesson is a five-minute teaching page, not a quiz.** `lesson.v5` returns a
one-sentence promise, 1-3 focused course concepts, 2-3 teaching sections, and
one small assignment. Real-world usage and "when not to use it" boundaries are
woven into the section bodies; there is no separate real-world or closing block.
Each section carries exactly one visual — a comparison table (always at least
one), numbered steps, two role cards, an accordion, tabs, a code snippet, or
short bullets — and consecutive sections cannot repeat the same visual kind.
Total visible text is budgeted at 260-380 words, with 140-240 words of body
prose. The lesson page renders a sticky course header, lesson sidebar with
completion ticks, a sourced header photo, the sections, the assignment, and a
Mark complete button. Questions are generated with the lesson but are not shown
there; the separate Final quiz page aggregates two questions per lesson into one
course-level attempt. Old lessons with only Markdown still render through the
same page with the structured sections omitted.

**Prompt caching depends on the prefix size.** The static system prompt and
per-course context carry `cache_control: {type: "ephemeral"}`. On Claude Haiku
4.5 the minimum cacheable prefix is **4,096 tokens**. A normal-mode lesson
prefix is about 2.9k, so Anthropic silently skips caching (the live normal run
recorded zero cache reads). Deep mode's full outline pushes the prefix over the
threshold, and the live deep run did hit the cache (175k cache-read tokens). The
plan's "~1.5k cached" assumption is too low for normal mode. Breakpoints remain
in place for a larger prefix or a `MODEL_DEEP` with a lower minimum.

**Failures degrade to a readable course.** A failed lesson marks the course
`partial`; completed lessons remain readable and a retry fills the gaps. An
analysis or outline failure marks it `failed`, with only the failed work left to
redo.

**Cost and audit trail.** Every model call, including retries and repairs, is a
row in `llm_calls` with model, prompt version, tokens, cache reads, latency, and
stop reason. The course page shows an estimated cost.

## API contract

The HTTP surface is committed twice, for two different jobs:

- `postman/specs/learn-anything.openapi.yaml` — the interface for tooling.
- `postman/collections/learn-anything/` — a runnable Postman v3 collection with
  request-level assertions and saved examples.
- `postman/environments/Learn Anything Local.environment.yaml` — `baseUrl`.

```bash
postman collection lint postman/collections/learn-anything
postman environment lint postman/environments
postman spec lint postman/specs/learn-anything.openapi.yaml --issueType=syntax
```

Collection order is create → list → detail → progress → lesson → attempt →
history. The create and get-course requests capture `topicId` and `lessonId` for
the later requests.

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/topics` | `{prompt, mode}` → `{id}`, enqueues pipeline |
| GET | `/api/topics` | list courses with counts |
| GET | `/api/topics/:id` | topic, subtopics, lesson stubs |
| GET | `/api/topics/:id/progress` | stage + done/total (polled) |
| POST | `/api/topics/:id/retry` | resume failed stages |
| DELETE | `/api/topics/:id` | cascade delete |
| GET | `/api/topics/:id/attempts` | attempt history |
| GET | `/api/lessons/:id` | teaching content + public questions (no answers) |
| POST | `/api/lessons/:id/complete` | mark a lesson complete |
| POST | `/api/lessons/:id/attempts` | legacy per-lesson attempt endpoint |
| GET | `/api/topics/:id/quiz` | final quiz questions (no answers) |
| POST | `/api/topics/:id/quiz/attempts` | grade and save the final quiz |

## Verification

```bash
pnpm test          # grading, lint, shuffle, schemas, answer-leak tests
pnpm typecheck
pnpm build
pnpm gen "test"    # live pipeline check; needs ANTHROPIC_API_KEY
```

The tests are offline: recorded fixtures, no live API calls. A live `pnpm gen`
is the only check that exercises the real model, caching, and the repair path.

The normal and deep runs below predate the compact lesson format and the
course-level concepts. The current v4 schema, prompt, lint, seeded demo, and
lesson page are covered by the offline suite and a manual UI pass. A live v4
generation is the remaining check.

## Live verification (2026-11-11)

Normal mode, `pnpm gen "Photosynthesis"`: **ready, 5/5 lessons, 28 questions**,
41k input / 17k output, **~$0.13**, zero cache reads (the 2.9k lesson prefix is
below Haiku 4.5's 4,096-token cache minimum).

Deep mode, same topic: the pre-tuning run produced 5 subtopics / 28 lessons.
13/28 lessons were ready when the account returned **"Your credit balance is too
low"** — 10 of the 15 failures were billing, not prompt failures. It cost ~$0.60
before stopping. After that run, deep is capped at 3–4 subtopics and 4–5 lessons
per unit (12–20 lessons), options/order items allow 240 characters, and soft
prose issues no longer trigger paid repairs. Those changes pass typecheck and the offline test suite, but they still need a
clean live deep run once the account has credits.

### v3 compact lessons (latest)

`pnpm gen "Event-Driven Architecture"` produced **5/5 ready lessons** after one
resume. Each lesson is **291-327 words total**, with a **108-161 word body**.
The analyze step extracted **5 course-level concepts**; each lesson focuses on
2-3 of them and the lesson page shows "concept X of 5". The initial run was 2/5
ready because a few correct options were paraphrases; those lessons were
accepted with grounding warnings after the repair budget, so the course could
finish. Total cost for the first run plus the resume was about **$0.16**.

## Known limits (deliberate)

- Local, single-user only. No auth, no `owner_id`, no queue service.
- One model path: Claude Haiku 4.5 via `ANTHROPIC_MODEL`. `MODEL_DEEP` exists as
  an env var but ships unset and is not exposed in the UI.
- The installed Anthropic SDK (v1.7) does not expose a `temperature` parameter,
  so the code does not send one. Quality is carried by the prompt contracts,
  schema validation, and quiz lint instead.
- No image-generation API: lesson headers use LoremFlickr keyword photos with a
  gradient fallback.
- No streaming tokens into the page, PDF export, search, share links, or editing
  generated content.
- Vercel/serverless deployment is out of scope: the in-process worker needs a
  long-lived Node process (`next start`, a VPS, Fly, Render).
