Event Design and Operational Considerations

Designing Clear and Robust Events

An event-driven system is only as good as the events that flow through it. Because producers and consumers are decoupled, the event payload itself becomes the API contract between them.

Clear event naming and message structure are critical. Events should always be named in the past tense to reflect that they are historical facts (e.g., `invoice_paid`, not `pay_invoice`). The structure should be predictable, often using a map or a struct to clearly label the data.

# Good Event Structure
            %{
              event_type: :invoice_paid,
              event_id: "evt_987654",
              timestamp: ~U[2023-10-27 10:00:00Z],
              data: %{invoice_id: "inv_123", amount: 5000}
            }

By including metadata like an `event_id` and `timestamp`, handlers can track the flow of events and implement necessary operational safeguards.

Operational Safeguards

When you decouple systems, you trade code complexity for operational complexity. Handlers must be designed defensively to survive the realities of asynchronous environments.

Validation and Unexpected Messages

Because any process can send a message to any mailbox, handlers must validate input. A GenServer should always include a catch-all `handle_info/2` clause to safely discard unexpected messages. If unhandled, these messages will sit in the mailbox forever, eventually crashing the node due to memory exhaustion.

Idempotency and Duplication

Networks retry failed requests. Your handler might receive the same `invoice_paid` event twice. Handlers must be idempotent, meaning they can safely process duplicates. You might achieve this by storing the `event_id` in the database and ignoring the event if that ID has already been processed.

Back Pressure

If a producer generates events faster than a consumer can process them, the consumer's mailbox will grow infinitely. Implementing back pressure—such as using synchronous `calls` when the queue gets too large, forcing the producer to slow down—is essential for system stability.

Observability

In a sequential program, a stack trace tells you exactly what failed. In an event-driven system, an event might pass through five different processes. You must implement robust logging and tracing (often using the `event_id`) to monitor the flow and debug failures.

When NOT to use Event-Driven Design

Despite its power, event-driven complexity is not always justified.

If a workflow is strictly linear, requires immediate consistency (e.g., checking a bank balance before allowing a withdrawal), and does not involve long-running background tasks, a simple synchronous design is more appropriate. Introducing PubSub and GenServers for a basic CRUD (Create, Read, Update, Delete) application will only make the code harder to read and debug without providing tangible benefits.

Always default to synchronous code, and introduce event-driven patterns only when you need responsiveness, decoupling, or scale.
