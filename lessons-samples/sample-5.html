GenServer as a Stateful Event Handler

Introducing the GenServer

When building event-driven systems, event handlers often need to remember things. A shopping cart handler needs to remember the items added; a rate-limiter needs to remember how many requests a user made recently.

In Elixir, the standard way to build a long-running process that holds state and reacts to events is by using the GenServer (Generic Server) OTP behavior. A GenServer abstracts away the raw `receive` loop and recursion we built earlier, providing a clean, standardized interface for handling messages and maintaining state.

Calls, Casts, and Info

A GenServer categorizes incoming messages (events) into three distinct types, each with its own callback function. Understanding the difference between them is critical for designing efficient handlers.

`handle_call/3`

Use a `call` when the sender needs a reply and is willing to wait (block) for it.

Example: A web request asks the Shopping Cart GenServer for the current total. The web request must wait for the GenServer to calculate and return the total before rendering the page.

`handle_cast/2`

Use a `cast` when the sender is just firing off an event and does not expect a reply.

Example: A user clicks "Add to Cart". The web request sends a `cast` to the GenServer to add the item and immediately confirms to the user, without waiting for the GenServer to finish processing.

`handle_info/2`

Use `info` to handle raw Elixir messages sent via `send/2`, or system messages like timeouts and process monitoring.

Example: A timer goes off, sending a raw message to the GenServer to clear the cart if it has been inactive for 30 minutes.

State Updates in Action

Let's trace how a GenServer updates its internal state when it receives an asynchronous event (`cast`).

defmodule CounterHandler do
              use GenServer

              # The callback triggered by a cast event
              def handle_cast({:increment, amount}, current_state) do
                # 1. Calculate the new state based on the event
                new_state = current_state + amount
    
                # 2. Return a tuple telling OTP to continue with the new state
                {:noreply, new_state}
              end
            end

When an `{:increment, 5}` event arrives, OTP automatically extracts the message from the mailbox and passes it to `handle_cast`, along with the `current_state` (let's say it's `10`).

The function calculates the `new_state` (`15`) and returns `{:noreply, 15}`. OTP takes that `15`, holds onto it, and passes it back into the callback the next time an event arrives. You never write a recursive loop; OTP handles the state transition seamlessly.
