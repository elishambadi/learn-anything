Supervision and Fault Tolerance

The "Let It Crash" Philosophy

In traditional software development, developers are taught to write defensive code. We wrap everything in `try/catch` blocks, attempting to anticipate and handle every possible error to prevent the application from crashing.

Elixir and OTP embrace a radically different approach: "Let it crash."

Because Elixir processes are completely isolated, a crash in one process does not affect the rest of the system. Instead of writing complex defensive code to handle unexpected states, we allow the process to fail cleanly. We then rely on a specialized OTP component to detect the failure and restore the system to a known, healthy state.

Supervisors and Workers

This recovery mechanism is built on a strict hierarchy of processes, dividing your application into two distinct roles.

Worker Processes

Workers are the processes that actually do the work. Your GenServers, event handlers, and background tasks are workers. If a worker receives a malformed event or loses a database connection, it simply crashes.

Supervisor Processes

Supervisors do no application work. Their only job is to monitor worker processes (or other supervisors). If a worker crashes, the supervisor detects it and immediately restarts the worker from its initial, clean state.

By structuring resilient event-driven services this way, transient bugs (like a temporary network blip) are solved automatically. The handler crashes, the supervisor restarts it, and the handler pulls the next event from the queue as if nothing happened.

The Danger of Duplicate Effects

While supervision is incredibly powerful, it introduces a critical design consideration for event handlers.

Imagine an event handler that processes a `payment_requested` event. It successfully charges the user's credit card via an external API, but then crashes while trying to save the receipt to the database.

The supervisor will restart the handler. Depending on how your event queue is configured, the handler might receive that exact same `payment_requested` event again. If it processes it blindly, it will charge the user a second time.

To safely use restarts, event handlers must be designed with idempotency in mind. Idempotency means that applying an operation multiple times has the same result as applying it once.

Practical Advice: Always check if an action has already been performed (e.g., querying the database for an existing transaction ID) before executing side effects like external API calls. Supervision guarantees your handler will stay alive, but you must guarantee it behaves safely when retrying events.
