PubSub and Event Distribution

Decoupling with Publish-Subscribe

Up to this point, we have discussed direct process messaging: Process A sends an event directly to Process B's mailbox using its specific Process ID (PID).

While direct messaging is fast and efficient, it creates tight coupling. The event producer must know exactly who the consumers are and how to reach them. If we add a new feature that also needs to react to that event, we have to rewrite the producer's code to send a message to the new handler.

To achieve true loose coupling in event-driven systems, we use the Publish-Subscribe (PubSub) pattern.

How PubSub Works

In a PubSub system, communication is routed through "topics" (named channels) rather than direct addresses.

01

Subscribe

Interested processes (consumers) tell the PubSub system, "I want to receive all events published to the topic named 'orders'."

02

Publish

An event producer simply tells the PubSub system, "Here is a new `order_placed` event. Broadcast it to the 'orders' topic."

03

Distribute

The PubSub system automatically copies and delivers the event to the mailboxes of every process currently subscribed to that topic.

By using PubSub, the producer has zero knowledge of the consumers. It just shouts into the void, and the PubSub system ensures anyone listening gets the message. You can add or remove subscribers dynamically without ever touching the producer's code.

Phoenix.PubSub in Practice

In the Elixir ecosystem, Phoenix.PubSub is the standard library for this pattern. It is incredibly fast, distributed out-of-the-box (meaning it works across multiple servers), and integrates seamlessly with standard Elixir processes.

ScenarioDirect MessagingPhoenix.PubSub
TargetA single, specific PIDA string-based Topic (e.g., `"chat:room:42"`)
Use CaseA supervisor talking to its workerBroadcasting data to many unknown listeners
CouplingHigh (Sender knows Receiver)Low (Sender only knows the Topic)

Practical Use Case:

Imagine a real-time chat application. When a user sends a message, the web request doesn't loop through thousands of connected users to send them the message directly. Instead, it publishes a `new_message` event to the `"chat:room_1"` topic via Phoenix.PubSub.

Every connected user's web socket is backed by a lightweight Elixir process that has subscribed to that topic. Phoenix.PubSub instantly delivers the message to all of their mailboxes, and their individual processes push the update to their screens. This allows the system to scale to millions of concurrent users effortlessly.
